# 显示路径性能基线（配置机制重构前实测）

> 整条链路里 **USB Full-Speed 是唯一瓶颈**：实测 **1.15 MB/s**（XHCI 口，= 物理天花板的 94%），
> 比最慢的解码器还慢 **28 倍**、比面板总线慢 **58 倍**。所以库侧的刷屏优化换不来实际帧率，
> 而面板总线降频几乎无损。

## TL;DR

五项指标，全部**真机实测**，无推算：

| 指标 | 实测 |
| --- | --- |
| 传输（USB Full-Speed） | **1.15 MB/s**（XHCI 口，天花板的 94%）；**0.878 MB/s 只在 USB 1.1 的 OHCI 口上出现** |
| 解码 | QOI **15.86** / RLE **31.53** / LZ4 60.64 MPix/s |
| 刷图（单带 480×8） | **119 µs/带**，64.3 MB/s |
| TFT 原始 fps | **217 fps** @50 MHz 总线；**487 fps** @div=1.0 |
| PIO 8080 带宽 | **66.6 / 133.1 / 149.7 MB/s**（50 / 100 / 112.5 MHz） |

- **瓶颈在 USB**：面板总线比链路快 76×，最慢解码器比链路快 36×。
- **面板总线有 4 倍余量**（50 MHz 只用掉上限的 44%），**降频几乎无损**。
- PIO 规律实测为 **3 周期/次 16 位写 = 0.667 B/周期**，三个时钟点精确线性；`div < 1` 非法。

## 测量环境与方法

- 目标：RP2350（`pico2`），面板 `pico_dm_qd3503728`，16 位 I8080 并口，clk_sys 225 MHz。
- 传输那一项的主机是 RK3588 板的 **OHCI 根端口**（`dmesg`: `using ohci-platform`）。**这一点重要**，见"漂移"。
- 所有运行时数字用 `time_us_32()` 在设备侧取，走配置里的调试串口（115200）输出。

### 承载这些测量的代码

| 位置 | 测什么 |
| --- | --- |
| `pico-display-lib/examples/bench_bus_bandwidth.c` | PIO 8080 带宽、整屏时间 |
| `pico-display-lib/examples/bench_screen_fps.c` | TFT 原始刷新率 |
| `pico-display-lib/examples/bench_band_flush.c` | 单带刷图耗时（含窗口命令开销） |
| `Pico-USB-Display/bench/decode_bench.c` | QOI / RLE / LZ4 解码吞吐（自带往返校验） |
| `Pico-USB-Display/tests/test_ep1_throughput.py` | 链路速率（配 `PUD_EP1_SINK=1` 构型） |

前四项各有独立 CMake 入口，不需要 USB 主机、内核驱动或合成器：

```bash
# 库侧的三个（examples/ 是独立入口，可直接作为顶层构建）
cmake -S examples -B build -DPICO_BOARD=pico2 -DPUD_CONFIG=pico_dm_qd3503728 \
      -DPUD_BUS_CLK_KHZ=112500        # 覆盖面板时钟，专供总线基准
cmake --build build -j8

# 解码基准
cmake -S bench -B build-bench -DPICO_BOARD=pico2 -DPUD_CONFIG=pico_dm_qd3503728
cmake --build build-bench -j8

# 链路：先烧 PUD_EP1_SINK=1 构型，再由主机侧跑（需 pyusb，且 pud 驱动必须未绑定）
cmake -S . -B build-sink -DPICO_BOARD=pico2 -DPUD_CONFIG=pico_dm_qd3503728 -DPUD_EP1_SINK=1
python3 tests/test_ep1_throughput.py --frames 40
```

## 1. 传输（USB EP1，Full-Speed）

`PUD_EP1_SINK=1` 构型（收下即丢弃，不解码不刷屏）→ 纯链路。
**同一块设备、同一固件、同一脚本，换主机/端口能差 31%**，而且差别几乎全在主机控制器**类型**上：

| 载荷高度 | 载荷 | RK Bus003（直插根口） | 本机 root hub | RK Bus005（**经 TT**） |
| --- | --- | --- | --- | --- |
| 8 | 11115 B | 1.136 MB/s | 1.101 MB/s | 0.794 MB/s |
| 32 | 44481 B | 1.147 MB/s | 1.134 MB/s | 0.872 MB/s |
| 128 | 177764 B | 1.148 MB/s | 1.139 MB/s | 0.880 MB/s |
| 320 | 444352 B | 1.148 MB/s | 1.138 MB/s | 0.878 MB/s |
| **达成率**（天花板 1.216） | | **94.4%** | **94%** | **72%** |
| **离散度** | | **1.0%** | 3.3% | 9.8% |

**结论：设备侧没问题，速率是 94% 的天花板，两个直插根口上完全一致（1.139 / 1.148）。**

**0.878 MB/s 那一列是拓扑损耗，来自路径里的 hub Transaction Translator（TT），不是设备、
也不是主机控制器型号的问题。** 仓库里早已实测过同一效应
（[`codec-selection` 姊妹笔记](../../../notes/scripts-measurements.md)：经 480M hub
**0.817 / 0.833 / 0.833 MB/s** vs 直插 xHCI 根口 **1.132 MB/s**，低约 28%，
结论是"拓扑差异，不是设备性能"）。本次的 0.878 与该 TT 已测值相差约 6%，而与根口值相距甚远。

三组都满足"速率随载荷增大持平 ⇒ 链路受限"。

> **归因更正**：初稿把这一列写成"USB 1.1 的 `ohci-platform` 端口缺陷"，那是**未经证实的推测**，
> 且被仓库既有的 TT 实测否掉。端口确实枚举在 `ohci-platform` 根hub 上，**但造成 30% 损耗的
> 已知机制是 TT**；把两者当成因果是没有依据的。

> 天花板 1.216 MB/s = 每毫秒 19 × 64 B（Full-Speed 上 64 字节 MPS 端点的物理上限）。

## 2. 解码

480×64（30720 px）的合成图，用各自的树内编码器压一次，再解 32 次；**解码结果必须与源图逐字节一致才报时间**。

| 编码 | 压缩后 | µs/带 | 吞吐 | 折算整屏 |
| --- | --- | --- | --- | --- |
| QOI | 5974 B | 1936 | **15.86 MPix/s** | 19.4 ms |
| RLE | 11020 B | 974 | **31.53 MPix/s** | 9.7 ms |
| LZ4 | 347 B | 506 | 60.64 MPix/s | 5.1 ms |

**LZ4 那一格偏高、不可直接引用**：合成图恰好极容易被它压（30720 px 只用 347 B），解码接近 `memcpy` 连续段。
QOI / RLE 的数字可信。**QOI 是最慢的解码器**，这一点决定了换 HS 之后的瓶颈归属。

## 3. 刷图（单带）

480×8 = 3840 px / 7680 B 每带，随机 y 位置刷 256 次：

- **119 µs/带**，8370 带/s，**64.3 MB/s**（略低于整屏 66.6，差的就是每带的窗口命令）。
- 整屏按 8 行/带切成 40 带 → 合计 **4760 µs**，而**一次整屏 flush 只要 4612 µs**：
  **分带多花 3.2%**，这就是 `tft_set_addr_win()`（CASET/RASET）的真实开销。
- 库侧要改分带策略时，这个 3.2% 就是收益上限。

## 4. TFT 原始刷新率

64 帧整屏 flush 计时：**216.81 fps**（295187 µs），与总线基准的 4612 µs/帧互相印证。

## 5. PIO 8080 带宽

PIO 程序每条写两条指令（`out pins,16 side 0` + `nop side 1`），分频
`clk_div = DEFAULT_PIO_CLK_KHZ / 2 / TFT_BUS_CLK_KHZ`：

| 总线时钟 | clk_div | PIO 时钟 | **实测带宽** | 整屏 | fps |
| --- | --- | --- | --- | --- | --- |
| 50 MHz（面板实际值） | 2.25 | 100 MHz | **66.60 MB/s** | 4612 µs | 217 |
| 100 MHz | 1.125 | 200 MHz | **133.08 MB/s** | 2308 µs | 433 |
| 112.5 MHz | **1.000** | **225 MHz（= clk_sys）** | **149.68 MB/s** | 2052 µs | 487 |
| 150 MHz | 0.750 | 非法 | 无输出（传输不完成） | — | — |

**三点精确线性 ⇒ 每个 16 位写实际占 3 个 PIO 周期（0.667 B/周期）**，而不是源码看起来的 2 个。
这条规律是从实测反推的，不是推导。

**`clk_div < 1` 不合法**（硬件分频器要求整数部分 ≥ 1），所以 PIO 不可能超过 clk_sys，
**天花板就是 ~150 MB/s**。

## 量级关系

```text
面板总线   66.6 MB/s  ┃━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┫ 58×
QOI 解码   31.7 MB/s  ┃━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┫       28×
USB 链路    1.15 MB/s ┃━┫                                            ← 瓶颈
```

端到端整屏约 **57 ms**（≈65 KB/屏 ÷ 1.15 MB/s），而面板本身 **4.6 ms** 就能刷完一整屏。
**换成 USB 1.1 的 OHCI 口会掉到 74 ms**，但量级关系不变：瓶颈始终在 USB。

**推论（已验证）**：在 Full-Speed 之下，分带策略、PIO 调频、解码器优化**都不会带来可感知的收益**；
反过来，面板总线降频也几乎无损，功耗与信号完整性有大量余量。

**推论（未验证）**：只有换成 High Speed 才会把瓶颈搬到 QOI 解码器（按其 15.86 MPix/s 折算整屏 19.4 ms
≈ 52 fps）。**RP2350 的 USB 控制器只支持 Full-Speed**（实枚举为 `new full-speed USB device`，
SDK 的 USB 寄存器集只有 FS 相关控制位），所以这不是固件能改的，需换主控。

## 边界与陷阱

### `DECODER_STATS` 的 `flush_us` 在默认路径下不是传输时间

`STAT_FLUSH_T0/ADD` 夹的是 `tft_video_flush()` / `tft_async_video_flush()` 调用本身。默认
`QOI_NONCALLBACK=2` 走**异步**路径：调用立刻返回，真正的等待在 `tft_async_video_wait()`（窗口之外）。
所以 `flush_us / pixels` 会给出 2.3 GB/s 这种物理上不可能的数——**那是排队，不是传输**。
要用它量总线得改 `-DQOI_NONCALLBACK=0` 走同步路径。

### 总线基准的时钟覆盖只对基准有效

`-DPUD_BUS_CLK_KHZ` 会把面板推到它并不需要的频率上（150 MHz 时 PIO 传输直接不完成）。
它高于面板所需时画面可能不正确——**这是总线基准，不是可用的显示配置**。

### 速率是会话属性

绝对 MB/s 依赖主机/端口、压缩内容与当轮负载。引用时必须带上条件。

## 与既有笔记的漂移登记

**链路速率：既有笔记 1.11~1.13 MB/s —— 已复现，不是漂移。**

- 旧值出处 `Pico-USB-Display/notes/codec-selection.md`（"链路实测 1.11~1.13 MB/s……= 全速理论上限
  1.216 MB/s 的 93%"）与 `notes/pitfalls-toolchain.md`（1.130 / 1.131 MB/s）。
- 在 **RK Bus003（XHCI）** 上重测 **1.148 MB/s（94.4%）**、在**本机 root hub** 上 **1.139 MB/s（94%）**，
  与旧值在测量误差内一致 ⇒ **那条数据本身没错**。
- **旧值不删**，两组都保留。另有一个**具有误导性的低值来源**：路径里带 **hub TT** 时只有
  **0.878 MB/s（72%）**（仓库既有实测 0.817~0.833，同源）。**引用时不要拿它代表设备能力**；
  量吞吐前先看拓扑，全速设备别挂在 hub 后面。
- **三轮都成立的结论**：速率随载荷增大持平 ⇒ 链路受限；天花板都是 1.216 MB/s。

## 重构后要比对什么

配置机制重构（分层 + schema + 配置期校验）动的是构建层，比对项按此排序：

1. **静态尺寸**：`DECODER_TYPE=6` 时 FLASH 152440 / RAM 479648；`DECODER_TYPE=3` 时
   148528 / 378144；加 `DECODER_STATS=1` 时 152664 / 479680。应逐字节一致。
2. **编译定义全集**：`-D` 集合必须一致。**例外**是 7 个本应修掉的空值定义：
   `INDEV_PIN_IRQ`、`TFT_X_OFFS`、`TFT_Y_OFFS`、`TFT_MODEL_MD144_SPI_V04`、`TFT_MODEL_P169H002`、
   `TFT_MODEL_YT280S030`、`TFT_MODEL_YT350S006` —— 它们被发成 `=""`（字符串字面量），
   击穿 `config.h` 的 `#ifndef` 默认值，且 `#elif TFT_MODEL_*` 会变成硬编译错误。
   目前没炸只因那三处都在 `#if TFT_DRV_USE_<驱动>`（当前为 0）里。
3. **`DECODER_STATS=1` 必须能链接**（重构前它是坏的：计数器定义在拆分中丢失，已修）。
4. **五项实测不应变差**——但在 Full-Speed 下它们本来也不该变，所以这一项主要是防回归。
